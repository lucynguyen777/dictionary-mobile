# Reader PDF Implementation Preparation

## Status
PDF extraction is still disabled in the Reader import route. The parser prototype now has:
- a `pdfjs-dist` dependency for PDF.js-style extraction;
- `extractPdfReaderText()` and `extractPdfReaderDocument()` in `data/readerImport.ts`;
- fixture tests for digital, empty, and image-only PDFs.

## Fixture Set
Fixture files live in `tests/fixtures/reader-pdf/` and are generated by:

```bash
node scripts/create-reader-pdf-fixtures.mjs
```

Committed fixtures:
- `digital-simple.pdf`: one-column selectable text.
- `digital-multiline.pdf`: multi-line paragraph ordering.
- `digital-columns.pdf`: layout-sensitive two-column text.
- `empty.pdf`: valid PDF with no text objects.
- `scanned-image.pdf`: image-only placeholder with no text objects.

The oversize fixture is intentionally not committed. Generate a local file larger than `MAX_READER_FILE_SIZE_BYTES` when parser tests are added.

## Selected Parser Path
Use a staged approach:

1. **Web-first prototype:** evaluate PDF.js-style extraction for Expo web using the committed digital fixtures.
2. **Native dev-client prototype:** evaluate `expo-pdf-text-extract` only in an Expo development build. It requires native APIs and must remain unavailable in Expo Go.
3. **No OCR in this slice:** image-only scanned PDFs must keep the OCR-required unsupported path.

Why this path:
- Current app can run Expo web without adding a native dev-client requirement.
- PDF.js-style extraction can be tested against repo-owned fixtures first.
- Native extraction can be added later if the product accepts a dev-client/native dependency.

## Acceptance Before Enabling PDF
- `digital-simple.pdf` extracts title/body text.
- `digital-multiline.pdf` preserves readable paragraph order.
- `digital-columns.pdf` either extracts readable order or returns a layout warning.
- `empty.pdf` maps to the existing empty-text error.
- `scanned-image.pdf` maps to OCR-required unsupported copy.
- Oversize local fixture hits the 10MB guard before parser work.
- Expo Go behavior is explicit if any native parser is selected.

## Next Implementation Slice
Keep `isEnabledReaderImportFormat('pdf')` false until manual smoke passes on Expo web and the UI copy clearly explains unsupported native/Expo Go behavior. The next implementation slice should wire PDF into `extractReaderDocument()` behind that gate, not before.

## Sources Checked
- PDF.js-style extraction is the selected web prototype path.
- `expo-pdf-text-extract` is native/dev-client only and not suitable for Expo Go.
- OCR remains out of scope.
